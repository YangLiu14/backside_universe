## 可复用部分与新增组件

可以保留现有 Hi3D 模型、照片/3DGS、Three.js 场景、镜头轨迹、自由探索和大部分页面。云端 GPU 浏览器直接打开相同场景，资产预先放到节点的本地 SSD/只读卷，手机只收画面和声音、发送操作，无需迁移到 Unreal。手机仍负责视频解码、显示和输入，并持续消耗视频流量。

| 部分 | 当前情况 | 云端需要补足 |
|---|---|---|
| 场景与资源 | 已有 Three.js、GLTF/Draco、近景流式加载 | 固定场景版本、本地资源路由；检查 WebGL 确实使用 GPU |
| 浏览器运行 | 目前由访客设备运行 | GPU 驱动、浏览器、虚拟显示、每会话独立运行状态和音频设备 |
| 画面与声音 | 多画布/图片/DOM，独立 HTMLAudio | 完整画面捕获、低延迟硬件编码、音频捕获和同步 |
| 传输 | HTTP 下载静态文件 | 视频通道、输入通道、断线重连；WebRTC 路线另含 ICE/STUN/TURN 方案 |
| 手机 UI | 原网页响应式触控 | 视频坐标映射、竖横屏切换、双指操作、声音启用、弱网降档 |
| 会话 | 同一用户在相册内保留页面 | 分配/排队、预热池、释放/重置、超时回收、隔离和健康检查 |
| 运维 | 静态站发布证据 | 每会话帧率/延迟/内存/显存/出口流量、容量和失败监控 |

现有相册和文字页面可以继续托管在 Netlify；进入作品后连接所分配的云端会话。两个访客自由行走时需要各自的相机与交互状态，不能共用一条视频和一个浏览器页面。不同会话可共享同一 GPU，但共享数量必须压测；磁盘缓存可共享，不代表解压后场景和纹理自动只占一份内存。

## 预载后重置：已有基础，还缺会话接口

[film.js](/Users/kloping/projects/ship_it_sunday/backside_universe/photo-demo/cases/sole-city/viewer/film.js:407) 在公开 `soleCityState` 前，已经渲染多个阶段来预热材质、反射与着色器，然后 `render(0)` 回原图。`home` 按钮停止播放、退出探索并回到进度 0，不重新下载全部模型。因此“后台先准备好，访客进来直接操作”在代码层面可行。

但 `home` 不是完整的新访客重置协议。声音状态、音频时间、语言/存储、下一站标签、指针捕获、未完成近景加载、连接身份等还需逐项归零或隔离。[street-walk.js](/Users/kloping/projects/ship_it_sunday/backside_universe/photo-demo/cases/sole-city/viewer/street-walk.js:27) 已有停止、释放指针和清除按键逻辑，可复用，但云端连接断开不必然触发远端浏览器失焦。

建议新增受控 `resetSession` 接口与生命周期：`loading → ready → leased → resetting → ready`。回收时先禁止旧连接输入、停止动画和音频、清除全部输入、回到指定视角和 UI 默认值，再验证状态，最后允许新访客连接。可保留只读资源和已解码纹理缓存；不把上一个访客的可变状态带入新会话。重置失败或 WebGL context 丢失的会话直接重建，不返回可分配池。该接口尚未实现。

[相册验收脚本](/Users/kloping/projects/ship_it_sunday/backside_universe/photo-demo/scripts/check-sole-album.cjs) 已验证隐藏时暂停、输入释放、回访保留场景，但它验收的是同一用户的作品切换，不足以证明多访客隔离。另需注意 [room.js](/Users/kloping/projects/ship_it_sunday/backside_universe/photo-demo/dist/cinema/room.js) 会依据 `document.hidden` 和相册 `inert` 状态暂停；把热会话简单塞进隐藏标签页可能令预热或渲染被暂停。应使用可正常渲染的独立虚拟显示，并明确区分“无人占用”和“页面不可见”。

## 手机输入、构图和捕获风险

- **双指输入：** 现有摇杆与画面环顾分别持有独立 `pointerId`，环顾还使用 `pointerType`。远程桌面把触摸转成一只鼠标，可能导致无法一边走一边转头。必须实测同按摇杆与拖动画面、移出区域、取消触摸、断线和系统切后台。若传输层不能保持语义，应做本地摇杆和环顾控件，向受控接口发送移动/视角指令；断线立即清零轴值。
- **竖屏：** 当前布局根据视口和 `pointer:coarse` 调整；服务器浏览器通常报告精细鼠标，即使接收端是手机。直接把桌面 16:9 视频缩到竖屏会缩小字和触控区。应明确远端 CSS 视口、DPR、触控模式与视频尺寸，校正黑边后的坐标映射；旋转时重新协商分辨率和绘图，不只旋转 `<video>`。
- **LOD 变化：** [city.js](/Users/kloping/projects/ship_it_sunday/backside_universe/photo-demo/cases/sole-city/viewer/city.js:114) 根据粗指针/设备内存选择 Draco 并行数；[near-buildings.js](/Users/kloping/projects/ship_it_sunday/backside_universe/photo-demo/cases/sole-city/viewer/near-buildings.js:29) 的移动端近景缓存上限 3 类、桌面端 6 类，加载并行数分别 1/2。云端视口与输入预设会改变实际负载，不能只按接收手机分辨率估计显存。
- **多层画面：** `#mesh`、`#gaussian`、原始照片、DOM 文案与控制区共同组成页面。仅对 `#mesh` 调用 `captureStream()` 会漏层。首个验证宜捕获专用浏览器窗口/虚拟显示的完整合成结果；以后可把文字/按钮放在接收端，视频只传场景。自建合成画布需要验证透明度、缩放、色彩与 GPU/CPU 拷贝成本。
- **声音：** `morning.m4a` 是独立 HTMLAudio。NVENC 编码视频不会自动包含它；必须给每会话单独音频输出并捕获/编码，避免串音。手机接收端还要处理播放声音需要用户手势的情况，不能承诺打开页面立即有声。

[record.cjs](/Users/kloping/projects/ship_it_sunday/backside_universe/photo-demo/cases/sole-city/record.cjs:4) 已能按固定进度合成照片、Gaussian 和网格并输出短片，master 模式还会复用原音频。这可复用到预渲染/混合体验；它逐帧 JPEG 送 ffmpeg 的流程是离线录制，不是现成低延迟串流服务。预渲染视频可以边下边播，适合默认浏览；任意自由行走仍需本地 3D 或云端实时会话。反向拖动短片还需短 GOP/关键帧与缓存策略，不能假定任意编码的 MP4 都能顺滑倒放。

## Selkies：当前默认不是 WebRTC

此次查阅的官方文档标记为 2.2.1。默认传输是 WebSockets：`--mode=websockets`，一个 TCP 端口，客户端使用 WebCodecs。WebRTC 是显式开启的 `--mode=webrtc`，可用 `--enable-dual-mode=true` 允许切换。默认 WebSocket 路线不需要 STUN/TURN；WebRTC 路线按网络条件配置 ICE 与中继。当前捕获/编码组件是 `pixelflux` 和 `pcmflux`，不能照抄旧教程的 GStreamer 架构。[官方组件与传输说明](https://docs.selkies.io/latest/components/)、[防火墙说明](https://docs.selkies.io/latest/firewall/)

选择依据应是目标手机与网络的实测：WebSocket 部署端口简单，但 TCP 丢包重传可能拖长交互等待；WebRTC 需要更完整的网络配置，可评估 UDP 路径在移动网络中的表现。不要把 TURN 计费无条件加到默认 WebSocket 方案，也不要假定所有 WebRTC 连接都会中继。

官方客户端支持嵌入自有网页，并声明支持触控/游戏手柄等输入；这不等于本项目的双指摇杆已通过验收。官方也按浏览器实际解码能力选择格式；WebSocket 下缺少 WebCodecs 的浏览器可能降为 JPEG 或使用 WASM 音频解码。这些降级会影响流量、耗电和延迟，需在实体 iPhone/Safari 与 Android/Chrome 上记录实际编码和传输路径。[官方 Web Client 文档](https://docs.selkies.io/latest/components/web-client/)

初次基线建议 H.264 8-bit 4:2:0、30 fps、约 720p 像素量，分别测试横屏 1280×720 与竖屏 720×1280；不是默认强制 AV1、4:4:4 或 10-bit。随后才比较码率、1080p 与更高帧率。图形驱动、NVENC 和浏览器 GPU 渲染必须分别验证：能跑 CUDA 不等于 Chromium 已使用硬件 WebGL。官方容器文档也区分 GPU、驱动和显示依赖。[Selkies 启动要求](https://docs.selkies.io/latest/start/)

## GPU 与 NVENC 约束

优先比较可提供完整图形驱动、硬件 H.264 编码和合适网络区域的 L4、A10、T4 等实例，而不是只按 CUDA 算力购买。当前 NVIDIA 官方矩阵列 L4 有 2 个 NVENC 引擎、A10/T4 各 1 个，三者最大编码会话栏均为 `Unrestricted`；A100 的 NVENC 数为 0，不能因为显存大就把它当首选视频渲染机。[NVIDIA 支持矩阵](https://developer.nvidia.com/video-encode-decode-support-matrix)

`Unrestricted` 不等于无限用户：实时渲染、CPU、系统内存、显存、编码吞吐与出口都可能先到瓶颈。编码器能同时编码几路，不等于场景能同时渲染几路。

官方文档存在版本差异：目前支持矩阵中 RTX 4090 等多款消费卡显示 12 会话，而固定版本 SDK 13.0 应用说明仍写 non-qualified 卡每系统合计 8 个。不能一概写成“每卡 8 个”或保证所有驱动都是 12 个；购买前应核对具体卡、虚拟化/图形授权、驱动和所用编码 API，并实际创建所需会话。专业卡仍受硬件资源约束。[SDK 13.0 NVENC 应用说明](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-application-note/index.html)

## 单 GPU 容量测试设计

本项目目前没有可信的“每卡 N 人”测量。T4/L4/A10 各自的 N 必须在固定镜像、场景版本、驱动、分辨率、DPR、画质和编码参数下产生。

1. 先测 1 个真实独立会话，再依次 2、4、8 个，发现瓶颈后在相邻数量间细测。每会话必须独立渲染和编码，不能把同一视频广播给 N 个播放器冒充 N 人容量。
2. 分别运行完整镜头、持续拖动、桥/药材铺等近景自由探索、近景首次加载和反复进退；既测错峰操作，也测所有访客同时进入重场景的峰值。每档先运行至少 10–15 分钟，候选容量再做持续运行与反复回收。
3. 同时记录 CPU/RSS、共享内存、GPU 显存基线/增量/峰值、图形和编码利用率、WebGL context 丢失、渲染帧时间、编码时间、发送队列、码率、丢帧、RTT、实际中继比例。单个浏览器进程的 GPU 内存统计可能不完整，要用节点总量增量复核。
4. 接收端用实体 iPhone/Safari 和 Android/Chrome，至少包含 Wi-Fi、移动网络、限速/丢包、竖横屏与双指。测从点击到首个能响应输入的解码画面，以及输入到画面变化的端到端延迟；只测服务器 FPS 无法代表手机体验。
5. 初始验收目标可设为 30 fps 流的持续输出不低于约 28 fps、同区域良好网络下输入到画面变化的 p95 不高于约 150–200 ms、无持续队列增长、无模型/音频串会话。**这是待讨论的产品门槛，不是已经取得的数值。** 保留 20% 左右资源余量，并验证新会话加入不会拖垮已玩用户。
6. 分开记录首次近景与已缓存近景；完成至少一次完整用户回收、故障重建、排队溢出与断线重连。最终报告同时给“稳定游玩容量”和“可接入新用户容量”，不能只报峰值启动成功数。

## 手机首玩时间：仅用于规划的未测预算

统一计时：用户点击进入，到手机出现可响应其操作的第一帧。下面假设同区域连接、正常移动网络、无排队；并不把原图/加载动画出现当作可玩。

| 分配到的状态 | 尚需完成的工作 | 自建方案初期规划范围，未测 |
|---|---|---:|
| 空闲热会话：浏览器、场景和 GPU 已 ready | 鉴权/分配、连接协商、关键帧和手机解码 | 2–5 秒 |
| VM 已开，镜像/资产已在本机，新建浏览器进程 | 启动显示/浏览器、解压/上传/编译、再连接 | 10–40 秒 |
| 冷 VM，预制镜像与资产可用 | 分配/开机、驱动/容器/浏览器启动、加载、连接 | 1–5 分钟 |

这些范围是工程预算，**不是云厂商 SLA，也不是由本地 31–36 秒测试折算得到**。GPU 缺库存、初次拉镜像/资产、跨区域连接或 TURN 绕路都可能超出。热会话足够时可以把等待压到数秒；“点开立刻可玩”依赖提前付费保持资源准备好，不能靠临时启动一台云机保证。

预热池同时占 GPU 显存、进程内存和一定计算/维护资源。作品、版本、语言、竖横屏若分池，可能出现一池空闲而另一池排队；要统计分池命中率，避免把总空闲数当可立即使用数。动态换分辨率比重复预热所有比例更节省槽位，但也必须测重新绘图和关键帧延迟。

托管方案的回收规则须单独纳入：腾讯 CAR 云 Web 可复用 URL，但退出后的清理和重新预热不是本项目的 `home` 重置。若实际周转为“游玩 5 分钟 + 清理/重置 1 分钟”，稳态所需槽位约为活跃游玩人数的 `6/5 = 1.2` 倍，还未计额外预热时间与突发余量；单一槽位无法同时服务当前访客与准备下一访客。S/M 是否满足场景仍需实测。相关厂商规则与价格见 [大陆价格核验](/Users/kloping/projects/ship_it_sunday/backside_universe/photo-demo/docs/CLOUD_RENDERING_CHINA_PRICING_NOTES.md)，不要把自建快速重置预算套用为托管承诺。

## 并发与成本计算的技术输入

自建所需 GPU 节点数应以 `ceil((活跃会话 + 回收中会话 + 空闲热备)/实测单卡容量)` 计算；每个区域和不能互换的资源池分别向上取整。再乘实际计费小时与节点单价，增加磁盘、控制服务和该网络计费模式下的出口/中继费用。开机预热的空闲 GPU 仍然产生费用，缩到零会失去热启动。

只算视频净负载时：`GB = 0.45 × 码率Mbps × 观看小时数 × 平均同时观看人数`。例如 4 Mbps 是约 30 MB/分钟、1.8 GB/小时；还要加音频、协议和重传。托管套餐若已含带宽，不能重复按自建出口计费。云端解决手机模型下载和渲染负担，但长时间游玩未必比下载一次模型更省流量。

对本项目最有信息量的下一步是用相同场景做一个真实手机接入的单 GPU/单路托管验证，再逐档增加独立会话；同时用现成录制能力评估“默认预渲染短片，点击自由探索再分配云会话”的混合体验。后者能减少真正占 GPU 的时长，但不等价于全程任意视角实时交互。
